## 1. Package name

**`com.aicreatorhub.ai_creator_hub`**

This project does not commit an `android/` folder — the CI workflow
(`.github/workflows/*.yml`) generates it fresh on every run with:

```
flutter create --platforms=android --org com.aicreatorhub --project-name ai_creator_hub .
```

Flutter derives the Android `applicationId` as `<org>.<project-name>`, so
every CI-built APK is packaged as `com.aicreatorhub.ai_creator_hub`. This
is the exact string to register in Google Cloud Console (§4/§6 below).

⚠️ If that `--org` or `--project-name` value in the workflow file is ever
changed, the applicationId changes too, and any OAuth client already
registered against the old package name will stop matching — Sign-In
will start failing with no code change needed to break it.

**Verification result:** ✅ confirmed by reading the CI workflow directly
— this is deterministic, not something that needs guessing from a build.

## 2. SHA-1 fingerprint required

Google Sign-In on Android checks the **package name + the SHA-1 of the
certificate the APK was actually signed with** against what's registered
in Cloud Console. Get this wrong and the picker still opens, but sign-in
fails with a `DEVELOPER_ERROR` (status code 10).

You need **two separate SHA-1 fingerprints** registered, because this
project uses two different signing keys depending on how the APK was
built:

| Build | Signed with | Stable across builds? |
|---|---|---|
| `flutter run` on your own machine | your machine's local debug keystore | ✅ yes, same key every time on that machine |
| CI release APK (`flutter build apk --release` in GitHub Actions) | **the runner's debug keystore** — see ⚠️ below | ❌ **no** |

⚠️ **This is the one real gap found in this project, and it needs a
decision from you before Google Sign-In will work reliably on the
CI-built APK:**

`android/app/build.gradle` (as generated by `flutter create`, unmodified
here) signs the `release` build type with `signingConfigs.debug` by
default — there's no custom release signing configured anywhere in this
repo. That's normally fine for a release *build*, but GitHub Actions
runners don't have a persistent debug keystore: `flutter create` /
`flutter build` generates a **new, random debug keystore on every run**
unless one is explicitly cached or checked in. That means:

- Every CI-built release APK is signed with a **different key**, so it
  has a **different SHA-1** each time.
- Registering "the" CI debug SHA-1 once will only work until the next
  CI run regenerates it.

You have two ways to fix this — pick one before doing real device
testing against a CI-built APK:

- **Recommended: add a real release signing config.** Generate one
  upload keystore, store it as a GitHub Actions secret (base64-encoded),
  decode it to a file in a new CI step before `flutter build apk
  --release`, and point `android/app/build.gradle`'s `signingConfigs.release`
  at it via a `key.properties` file. This gives you one stable SHA-1
  forever, and is what a real Play Store release needs anyway.
- **Simplest for your phone-only workflow: use Google Play App
  Signing.** Upload your first build (even unsigned/debug-signed) to a
  Play Console *Internal testing* track. Play re-signs the app with a
  key Google generates and holds for you — no local keystore, no
  `keytool`, no computer required. Play Console then shows you the
  exact SHA-1 to register (§3, option C).

Since neither of these is a code change to *this* repo (they're CI/CD
and Play Console configuration), nothing here was modified for it — this
section is guidance for your next step, not a gap in the current files.

**Verification result:** ⚠️ confirmed gap — no release signing config
exists in the generated `android/app/build.gradle` template, and none is
added by this repo's CI workflow either. Flagged, not fixed, per the
"no code changes unless absolutely required" instruction — fixing it
requires a keystore only you can generate/hold, which I can't fabricate
on your behalf.

## 3. How to obtain the SHA-1 fingerprint

**Option A — local debug keystore** (only useful if you ever get access
to a computer with the Flutter/Android SDK; matches only builds made on
*that* machine):

```
keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android -keypass android
```

(macOS/Linux path shown; Windows default is
`%USERPROFILE%\.android\debug.keystore`, same alias/passwords.)

**Option B — via GitHub Actions, without any local tooling** (fits your
phone-only workflow): the CI runner already has a JDK installed (see the
`actions/setup-java@v4` step, JDK 17), and every JDK ships `keytool`. You
can add a temporary workflow step to generate a real upload keystore and
print its SHA-1 directly in the Actions log:

```yaml
- name: Generate upload keystore and print SHA-1
  run: |
    keytool -genkeypair -v -keystore upload-keystore.jks \
      -alias upload -keyalg RSA -keysize 2048 -validity 10000 \
      -storepass CHANGE_ME -keypass CHANGE_ME \
      -dname "CN=Pak AI, OU=Pak AI, O=Pak AI, L=, S=, C=US"
    keytool -list -v -keystore upload-keystore.jks -alias upload -storepass CHANGE_ME
- uses: actions/upload-artifact@v4
  with:
    name: upload-keystore
    path: upload-keystore.jks
```

Run it once, copy the SHA-1 from the Actions log, download the
`upload-keystore.jks` artifact and save it somewhere safe (you'll need
the same file + password for every future signed build), then remove
the step (or keep it — re-running just regenerates a *different* key, so
don't rely on it running more than once for the same keystore).

**Option C — Google Play App Signing** (no keytool needed at all): Play
Console → your app → **Setup → App integrity** (formerly "App signing")
→ shows the **App signing key certificate** SHA-1 once you've uploaded
your first build to any track (including Internal testing). This is the
SHA-1 every Play-distributed build will actually be signed with in the
hands of users, regardless of what signed your local/CI build artifact —
register *this* one for a production listing.

**Verification result:** ✅ all three options are standard, unmodified
tooling already available to this project (JDK in CI, `keytool` in that
JDK, Play Console for anything you distribute there) — nothing needed
adding to make any of them possible.

## 4. How to create the Google OAuth Client ID

1. Go to [Google Cloud Console](https://console.cloud.google.com/) →
   create a new project (or pick an existing one) — no Firebase project
   needed for this, a plain Cloud project is enough.
2. **APIs & Services → OAuth consent screen** — configure this first;
   Cloud Console won't let you create a working OAuth client without it.
   - User type: **External** (unless every signer-in is inside your own
     Google Workspace org, which isn't the case for a public app).
   - App name: `Pak AI`, plus a support email and (once you have one) a
     privacy policy URL — this project already has an in-app
     `PrivacyPolicyScreen`; if you host that content on a public URL
     later, use that link here.
   - Scopes: add `email`, `profile`, `openid` — exactly what
     `GoogleAuthService` requests (`scopes: ['email', 'profile']`) in
     `welcome_screen.dart`. Nothing more.
   - While the app is in **Testing** publishing status, only Google
     accounts you explicitly add as **test users** can complete
     sign-in — everyone else sees an "app not verified" block. Add your
     own testing accounts here, or move the app to **In production**
     once you're ready for the public (basic, non-sensitive scopes like
     these don't require Google's manual verification review).
3. **APIs & Services → Library** — enable the **Google People API** (a
   long-standing safe default for resolving profile/email data; modern
   `email`/`profile`/`openid` scopes often work without it, but enabling
   it avoids a class of legacy failures).
4. **APIs & Services → Credentials → Create Credentials → OAuth client
   ID** — see §5/§6 for exactly which type and values to enter.

**Verification result:** N/A — this is external Console configuration,
outside the repo; nothing in the project needed to change for it.

## 5. Which OAuth type to choose

**Android.** Not "Web application," not "iOS."

The current implementation (`GoogleAuthService` in `welcome_screen.dart`)
calls `GoogleSignIn(scopes: ['email', 'profile']).signIn()` with no
`serverClientId` — it only reads the signed-in account's local profile
(name/email/photo) for display, it never sends anything to a backend for
verification. That flow only requires an **Android**-type OAuth client
registered against the package name + SHA-1 (§1/§2); nothing in app code
references the client ID directly, so there's no `CLIENT_ID` string to
paste into `pubspec.yaml`, `AndroidManifest.xml`, or any Dart file for
this to work.

You would only need an *additional* **Web application**-type OAuth
client if a future step adds a backend that needs to verify the user's
identity server-side (`GoogleSignIn(serverClientId: '...')` to get an
`idToken`/`serverAuthCode`) — out of scope for Step 19.3A, and not
something this step adds speculatively.

**Verification result:** ✅ confirmed against the actual scopes/call
already in `welcome_screen.dart` — no `serverClientId` is passed, so no
Web client and no client-ID string anywhere in the app is required.

## 6. Which package name to register

Register exactly: **`com.aicreatorhub.ai_creator_hub`** (§1) — paired
with each SHA-1 you obtain (§2/§3). You'll end up with two Android-type
OAuth client entries in the same Cloud project, same package name, one
per SHA-1:

- one for whichever debug/testing SHA-1 you use for local or ad-hoc
  device testing,
- one for the stable release SHA-1 (release keystore, or Play App
  Signing certificate — §2) that actually ships to users.

Both live under the same OAuth consent screen configured in §4 — you
don't need a second consent screen or a second Cloud project.

**Verification result:** ✅ same package-name confirmation as §1.

## 8. Final verification checklist (device-level, after Console setup)

- [ ] Package name in every registered OAuth client is exactly
      `com.aicreatorhub.ai_creator_hub` (copy-paste, not retyped — a
      single typo silently breaks matching).
- [ ] The SHA-1 registered matches the actual key that signed the APK
      you're testing right now — re-check §2's CI-debug-keystore caveat
      if testing a freshly-built CI artifact.
- [ ] OAuth consent screen is either Published, or your test Google
      account is explicitly listed under Test users.
- [ ] Test device/emulator has Google Play Services installed and an
      active Google account signed in at the OS level (a bare AOSP
      emulator without Play Services will fail every time, unrelated to
      any of the above).
- [ ] `INTERNET` permission — already present and already proven working
      in this project (release builds have made live Gemini API calls
      since Step 7), so `google_sign_in`'s own network needs are already
      covered; no manifest edit needed.
- [ ] Manual pass: tap "Continue with Google" → the real account picker
      opens → choose an account → app lands on Chat with that account's
      real name/photo/email showing on the Profile screen.
- [ ] If it still fails: pull `adb logcat` on the test device and filter
      for `ApiException`. Status code **10** = package name/SHA-1
      mismatch (re-check this file). **12501** = user simply cancelled
      the picker (not an error — the app already handles this by
      staying on Welcome). **7** = network error (check device
      connectivity, not Console config).
